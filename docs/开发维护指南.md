# 开发维护指南

本文面向后续功能修改、缺陷修复和数据维护，目标是让改动范围明确、可验证、可回滚。

## 1. 开发环境

- Node.js 22（Docker 镜像使用 Node 22 Bookworm）；
- npm 与 `package-lock.json`；
- SQLite 3；
- 建议在 Git 仓库中开发，任何生产修改前创建提交或标签。

首次安装：

```bash
npm ci
cp .env.example .env
npm run db:init
npm run dev -- --hostname 127.0.0.1 --port 3003
```

`db:init` 会生成客户端、同步结构并执行种子。种子包含演示账号且可能重置演示密码，只能用于新建或明确允许重置的环境。

## 3. 日常修改流程

1. 确认需求影响的角色、页面、API 和数据实体。
2. 先读取现有实现，不能只按页面文字推断业务规则。
3. 涉及数据时先复制数据库，并记录当前行数和完整性结果。
4. 实现最小范围修改，避免顺手改变无关行为。
5. 更新对应现行文档，不新增重复说明文件。
6. 运行类型检查、构建、数据检查和针对性人工测试。
7. 记录部署步骤、数据迁移和回滚条件。

## 4. 权限修改

权限至少检查三层：

- 页面是否允许进入；
- API 是否校验登录和角色；
- 查询/写入是否校验资源归属。

师父资源归属通常通过组织 `ownerId`、产品/任务 `createdById`、任务组织和报告会话链路判断。徒弟资源必须校验 `session.userId` 或报名关系。

不要依赖隐藏按钮作为权限控制，不要接受客户端提交的用户 ID、角色或所有者 ID 作为可信依据。

## 5. 数据模型修改

当前项目以 `prisma/schema.prisma` 为唯一结构来源，不保留长期漂移的手工 SQL 副本。

推荐流程：

```bash
cp prisma/dev.db /项目外安全目录/dev.db.before-change
npm run db:push
npm run db:generate
npm run test:integrity
```

生产环境不要运行 `db:init` 或 `db:seed`。删除字段、改唯一约束或改变关联删除行为时，必须先在数据库副本验证历史数据。

JSON 字段需要兼容旧数据：

- `Task.orderInfoJson`
- `Task.objectivesJson`
- `TrainingSession.customerStateJson`
- `ScoreReport.reportJson`

解析代码应提供默认值，不能让一条旧数据导致整个页面崩溃。

## 6. API 修改

Route Handler 的通用顺序：

1. 读取并校验当前用户；
2. 解析输入并做长度、枚举和范围校验；
3. 查询资源并验证归属；
4. 对多表写入使用事务；
5. 返回稳定的 JSON 或同源重定向；
6. 不向客户端返回密码哈希、密钥密文和内部异常堆栈。

外部 AI 调用应尽量放在数据库事务之外，但调用完成后仍需通过状态认领或乐观锁防止重复写入。

## 7. 前端修改

- 服务端页面优先直接查询 Prisma；
- 需要交互时才使用客户端组件；
- 表单前端限制必须在 API 端重复验证；
- 页面刷新不得无意创建重复会话或重复提交；
- 删除操作必须明确目标，并在服务端再次检查归属；
- 新增样式优先复用现有组件和 CSS 变量，清理被替代的选择器和图片。

首页使用五屏滚动、键盘导航和响应式布局。修改首页时同时检查桌面、窄屏、低高度窗口和 `prefers-reduced-motion`。

## 8. AI 与评分修改

不要只改提示词。模型输出变化至少会影响：

- `lib/types.ts`；
- `lib/ai/client.ts` 的解析与校验；
- `lib/scoring.ts` 的本地回退；
- 报告组件和成长聚合；
- 数据中的历史 `reportJson`；
- 正式考核和证书阈值。

模型返回永远视为不可信输入，应在服务端归一化分数、枚举、字符串长度和数组数量。

## 9. 文件与密钥

- `.env` 不提交、不打包、不通过聊天发送；
- 数据库备份放在项目目录之外；
- 签章只允许验证通过的 PNG；
- 更换 `AI_CONFIG_ENCRYPTION_KEY` 必须使用密钥轮换脚本迁移已有密文；
- 不能直接替换密钥后重启，否则数据库中的 API Key 将无法解密。

## 10. 已知维护重点

- 服务端补齐训练时间和轮次限制；
- 增强任务和报告输入校验；
- 统一 AI 报告总分、维度和风险封顶；
- 收紧手工报名的组织一致性；
- 证书编号改为精确核验并明确多考核归属；
- 保留不可变原始评分和复核历史；
- 数据量增长前规划 PostgreSQL、对象存储与多实例架构。
